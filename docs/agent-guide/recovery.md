# Continuity and recovery

Read for an actual interrupted handoff, missing queued requirements, concurrent-edit incident or conflicted checkout. Do not impose this workflow on an ordinary isolated bug.

## Current continuation

Reconcile the relevant current Git/working-tree state, instructions and task evidence. Preserve unrelated changes. Historical build/commit/status labels in `docs/SESSION-HANDOFF.md`, `docs/CURRENT-STATE.md` or old prompts are navigation evidence, not proof of current deployment. Search their relevant heading when resuming that work; do not automatically start the old queue. `docs/SESSION_HANDOFF.md` is an obsolete compatibility pointer. For a product/live claim, read [Delivery](delivery.md); a document-only continuation does not require live inspection.

If context becomes unreliable, inventory **every** pending requirement and local change, write a concrete task list and prepare a fresh-session handoff at an appropriate effort while staying in the saved Dropbox project. Do not automatically launch another task merely because an old handoff says to continue; follow the owner's current task-creation instruction. Keep implementation, checks, remote publication, listening and real-device acceptance distinct.

For desktop/mobile continuity, do not assume locally queued desktop messages reached the synchronized task. Before declaring a requirement missing, inspect available local queue/history evidence, record recoverable requirements, and mark truncated text rather than reconstructing it. Never expose private material/secrets in the recovery record.

## Conflicted shared work

Establish one writer for the shared checkout. If independent authorized work uses separate checkouts, that is a different concurrency boundary; do not describe it as two writers to the same files. Implementation normally remains in the saved Dropbox project. Preserve current work before destructive recovery and identify author/commit ownership; do not blindly stage marker-free conflict files, cherry-pick already integrated commits or treat pre-conflict green tests as current proof.

For a real conflict, capture the relevant checkout identities/status, unmerged index stages, rebase metadata and useful unstaged/untracked changes without secrets. Check current process/listener identity rather than trusting historical PIDs. Choose a reversible preservation-first recovery; ask only if a destructive/irreversible choice is outside current authority. Do not discard a hunk/artifact before accounting for it. Verify the resulting current state with checks appropriate to the recovered unit and release, not automatically the entire 2026 emergency itinerary for each small edit.

For cross-machine native packages use [Environment portability](motion-runtime.md#environment-portability). For rebuilding an approved visual use its exact current [source/design boundary](visuals.md), with source/candidate rendering when required. A historical recovery mandate is not permission to restore rejected Drivey, WAKE or retired PRIMORDIAL.
